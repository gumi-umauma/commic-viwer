# AIルール：スキーマ定義フェーズ

> このファイルはAI（Claude等）が**スキーマ定義フェーズ**で参照するルールです。

---

## このフェーズの目的

仕様をAPI・DBの型（スキーマ）で定義する。

- フロントエンドとバックエンドの契約になる
- 型があれば実装時のミスが減る
- ドキュメントが自動生成できる

---

## 前提条件

- **仕様書（spec/）が存在すること**
- 仕様書の概念をそのままスキーマに反映する

---

## 成果物

| ファイル                   | 内容                   | 備考             |
| -------------------------- | ---------------------- | ---------------- |
| `docs/schema/openapi.yaml` | API仕様（マスター）    | OpenAPI 3.x 形式 |
| `docs/schema/schema.sql`   | DBスキーマ（マスター） | DDL形式          |

### 生成ドキュメント（派生物）

| ファイル                | 生成方法                                      |
| ----------------------- | --------------------------------------------- |
| APIドキュメント（HTML） | Redoc / Swagger UI で openapi.yaml から生成   |
| DBドキュメント          | tbls でJSON出力 → LIMA EDR でグラフィカル表示 |

### ツール連携

- **API**: Redoc / Swagger UI で HTML ドキュメント生成
- **DB**: atlas でスキーマからDB生成・マイグレーション

## API設計ルール

### 設計方針: BFF（Backend For Frontend）

- **画面ごとに1つのAPIを設計**
- 共通の内容が多くの画面で出てきたら、RESTベースのAPIとして共通化を検討

### パス設計

| 項目             | ルール       | 例                              |
| ---------------- | ------------ | ------------------------------- |
| プレフィックス   | `/api/`      | -                               |
| エンドポイント名 | 画面名ベース | `/api/work-list`, `/api/viewer` |
| HTTPメソッド     | REST準拠     | GET/POST/PUT/DELETE             |

### 認証

- **JWT**（`Authorization: Bearer <token>` ヘッダー）

### レスポンス形式

- **成功時**: データをそのまま返す
- **エラー時**: Problem Details（RFC 7807）を使用

```json
// 成功時
{
  "id": "xxx",
  "title": "作品名",
  ...
}

// エラー時（Problem Details）
{
  "type": "https://example.com/errors/not-found",
  "title": "Not Found",
  "status": 404,
  "detail": "指定された作品が見つかりません"
}
```

### OpenAPI命名規則

| 項目        | ルール     | 例                                   |
| ----------- | ---------- | ------------------------------------ |
| operationId | camelCase  | `getWorkList`, `createBookmark`      |
| スキーマ名  | PascalCase | `Work`, `Volume`, `WorkListResponse` |
| タグ        | 不使用     | 増えてから検討                       |

## DB設計ルール

### 命名規則

| 項目       | ルール            | 例                                |
| ---------- | ----------------- | --------------------------------- |
| テーブル名 | 単数形            | `work`, `volume`, `user`          |
| カラム名   | snake_case        | `read_status`, `reading_progress` |
| 主キー     | `id`（UUID）      | `id UUID PRIMARY KEY`             |
| 外部キー   | `{テーブル名}_id` | `work_id`, `volume_id`            |
| 日時カラム | 必須              | `created_at`, `updated_at`        |

### データ型

| 項目         | ルール                                            |
| ------------ | ------------------------------------------------- |
| 日時         | `TIMESTAMPTZ`（UTC保存、表示時にJST変換）         |
| 文字列長     | 用途別に決定（タイトル=255、説明=TEXT等）         |
| ステータス値 | 明確なON/OFF → `BOOLEAN`、拡張可能性あり → `ENUM` |

### 削除方式

- 物理削除を基本とする

## 推奨方針

- 可能な限り仕様書（glossary.md）の用語に沿った命名を使用する
- スキーマ定義中に「この仕様だと表現できない」と気づいたら**仕様書に戻る**
- 仕様の矛盾・不足を発見したらAIがユーザーに報告する
